# Stepflow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `/stepflow` skill that turns a multi-step procedure into a localhost page with one-at-a-time steps, per-step `claude -p` spin-off chats, lessons, and a runbook export.

**Architecture:** Zero-dependency Node. `flow.mjs` owns the flow file (load/normalize/save, mutations, context prompt, runbook). `claude.mjs` runs one `claude -p` turn. `server.mjs` is the HTTP layer (token + Host guard, JSON API, serves `page.html`). `page.html` is vanilla JS.

**Tech Stack:** Node 24 (`node:http`, `node:test`, `node:child_process`, `node:crypto`), vanilla HTML/JS.

**Spec:** `docs/superpowers/specs/2026-11-12-stepflow-design.md`

## Global Constraints

- No npm dependencies. Everything lives in `plugins/AdamJ/skills/stepflow/`.
- Server binds `127.0.0.1` only. Every `/api/*` request needs header `x-stepflow-token` equal to `flow.token`, otherwise 403. A `Host` header other than `127.0.0.1:<port>` or `localhost:<port>` gets 403 on every route. The token is never logged.
- Flows live in `~/.stepflow/<yyyy-mm-dd>-<slug>/flow.json`. Writes are atomic (write `flow.json.tmp`, then rename) and serialized.
- Spin-off command: `claude -p --output-format json --permission-mode acceptEdits` + (`--session-id <uuid> --append-system-prompt-file <flowdir>/context-<stepId>.md` on the first turn | `--resume <sessionId>` after that) + `--allowedTools <...step.allowed>` when the list isn't empty. The message goes on stdin, and the process runs in `flow.cwd`. The binary is `process.env.STEPFLOW_CLAUDE ?? 'claude'`, used for test stubbing.
- Statuses: `pending | done | blocked | skipped`.

## Review Focus

1. A `claude` run that fails, exits non-zero, or prints invalid JSON: the page shows the error in the thread, and the step stays usable. (Task 2 test)
2. Two messages sent quickly on one step: the second gets 409 and no second process starts. (Task 3 test)
3. A hand-written `flow.json` missing ids, status, token or port: `normalize` fills them in, and existing values are kept on re-run. (Task 1 test)
4. A step body with `<script>` or HTML: rendered as text, never executed. (Task 4, escape before markdown)
5. A request from another origin (wrong token or Host): 403, and `claude` never runs. (Task 3 test)

### Task 1: Flow store, context prompt, runbook

**Files:** Create `scripts/flow.mjs` and `test/flow.test.mjs`. Paths are relative to `plugins/AdamJ/skills/stepflow/`.

**Interfaces (Produces):**
- `loadFlow(path): Flow` — reads the file, normalizes it, saves it if anything changed, and returns the flow.
- `normalize(flow): boolean` — fills in missing `id` (`s1`…), `status:'pending'`, `lesson:''`, `allowed:[]`, `messages:[]`, `token` (32 hex characters), `cwd` (defaults to `os.homedir()`). Returns true if anything changed.
- `createStore(path) -> { flow, update(fn): Promise<Flow> }` — `update` runs one mutation at a time (promise chain) and then saves atomically.
- `contextPrompt(flow, stepId): string` — the goal, the context, every step as `N. [status] title` followed by its lesson if there is one, and the line "You are helping the user with step N: <title>", with that step's body.
- `statusLine(flow): string` — one line, e.g. `Statuses now: 1 done, 2 blocked, 3 pending`.
- `renderRunbook(flow): string` — markdown: `# <title>`, the goal, then `## N. <title> — <status>` for each step, its body, and `> Lesson: …` when there is one. Ends with a "Needed attention" summary listing the steps that are blocked or have a lesson.

- [ ] Tests: `normalize` fills the fields and is idempotent (the second call returns false and the token doesn't change); concurrent `update`s both apply (two parallel pushes end up with two messages); `contextPrompt` includes the other steps' statuses and lessons; `renderRunbook` puts a step with a lesson under "Needed attention".
- [ ] Run `node --test test/` and confirm it fails, then implement, then confirm it passes, then commit.

### Task 2: Claude runner

**Files:** Create `scripts/claude.mjs`, `test/claude.test.mjs`, and `test/fake-claude.mjs`.

**Interfaces (Produces):** `runClaude({ message, cwd, sessionId, isFirst, contextFile, allowed, timeoutMs = 600000 }): Promise<{ text, sessionId, denials: [{ tool, input, rule }] , error? }>`. Here `rule` is `` `${tool_name}(${tool_input.command})` `` when there's a command, otherwise `tool_name`. It never rejects: spawn errors, non-zero exit, `is_error`, invalid JSON and timeouts (the process is killed) all resolve with `error` set.

`fake-claude.mjs` writes its argv to `$FAKE_LOG`, then prints JSON chosen by `$FAKE_MODE` (`ok` | `deny` | `bad` | `fail`). Tests set `STEPFLOW_CLAUDE=node` and pass the script path as the first argument, so the runner splits the env var on the first space into the binary and its leading arguments.

- [ ] Tests: on the first turn the args include `--session-id` and `--append-system-prompt-file`; on later turns they include `--resume` and no `--session-id`; `--allowedTools` is present only when `allowed` isn't empty; `deny` mode maps to `rule: 'Bash(curl x)'`; `bad` and `fail` modes resolve with `error`.
- [ ] Red → implement → green → commit.

### Task 3: HTTP server

**Files:** Create `scripts/server.mjs` and `test/server.test.mjs`.

**Interfaces:** `startServer(flowPath, { port?, open = true }) -> Promise<{ url, close() }>`. The port is taken from `flow.port` if it's free, otherwise from the OS (port 0), and saved. CLI: `node scripts/server.mjs <flow.json> [--no-open]` prints the URL and opens it with `start` / `open` / `xdg-open`.

Routes (each takes and returns JSON):
- `GET /?t=<token>` serves `page.html`. Token checking for the page happens in the API calls.
- `GET /api/flow` returns the flow without `token`.
- `POST /api/steps/:id/status {status}` sets the status.
- `POST /api/steps/:id/lesson {lesson}` sets the lesson.
- `POST /api/steps/:id/chat {message}` returns `{ messages }` or 409 if that step is busy. It records the user message, writes the context file on the first turn, prefixes `statusLine` on later turns, and calls `runClaude`. It then appends `{ role:'assistant', text, denials, error }`.
- `POST /api/steps/:id/allow {rule}` adds the rule to `step.allowed`, then runs the chat flow with "Approved — retry: <rule>".
- `POST /api/steps/:id/summarize` runs a chat turn asking for a 1–3 line lesson, sets `step.lesson` to the reply, and returns `{ lesson }`. The request and reply are not added to `messages`.
- `POST /api/export` writes `runbook.md` next to the flow and returns `{ path, markdown }`.
- `POST /api/finish` exports, responds, then closes the server and exits.

- [ ] Tests (using the fake claude): no token gives 403 and the fake is never called; a wrong Host gives 403; chat appends the assistant message; two parallel chats on one step give one 200 and one 409; `allow` adds the rule and the fake sees `--allowedTools`; export writes the file.
- [ ] Red → implement → green → commit.

### Task 4: Page

**Files:** Create `scripts/page.html`.

The page behaves like this:
- It reads the token from `?t=` and sends it on every fetch.
- Steps are listed top to bottom. A step header shows its number, title and a status badge, and clicking the header toggles it. Only one step is expanded at a time: on load, the first step that's `pending` or `blocked`.
- **Done** and **Skip** collapse the current step and expand the next pending step. **Blocked** keeps the step expanded and focuses its spin-off input.
- Step bodies are escaped and then run through a minimal markdown renderer that handles fenced code (with a copy button), inline code, bold, lists, paragraphs and links.
- The spin-off panel holds the thread and a textarea. Enter sends, and Shift+Enter adds a newline. While Claude works, the input is disabled and "Claude is working…" is shown. Each denial is listed as `<rule>` with an **Allow & retry** button, and errors are shown in red.
- The lesson textarea saves on blur, and **Summarize fix** fills it in.
- The footer has **Export runbook** (shows the markdown and offers a download) and **Finish**.
- Keyboard and accessibility: headers are buttons with `aria-expanded`.

- [ ] Verify: start the server on a sample flow with the fake claude and check by loading the page (headless Chrome screenshot if available) and through API calls. Commit.

### Task 5: SKILL.md + smoke run

**Files:** Create `SKILL.md`.

The skill has three modes:
1. `/stepflow` while instructions are in the conversation, or `/stepflow <task>`: Claude writes the steps (one action per step, commands in fenced blocks, `cwd` set) to `~/.stepflow/<date>-<slug>/flow.json`, starts the server detached (on Windows, `Start-Process node -ArgumentList ... -WindowStyle Hidden`), and tells the user the folder name.
2. `/stepflow <runbook.md path>`: Claude regenerates the steps with the lessons folded in. It fixes the commands, adds prerequisite steps, and drops steps that weren't needed. The lessons don't become separate notes.
3. `/stepflow <slug|folder>`: restarts the server for that flow only.

The main conversation should not repeat the steps in chat, so its token use stays low.

- [ ] Smoke run: create a 3-step sample flow, start the real server, and run one real spin-off turn against real `claude` through `curl` with the token. Confirm the reply is stored in `flow.json`. Commit.
